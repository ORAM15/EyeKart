# EYEKART — PHASE 6.5: SECURITY THREAT MODEL & GAP MATRIX
## External Integration Security Controls & Vulnerability Analysis (Version 1.0)

---

## 1. Executive Summary

Integrating live external rails (Safaricom Daraja, cloud object storage, KRA eTIMS, and SMS/email providers) expands EyeKart's threat surface beyond local client-server boundaries. 

This document provides a systematic threat model evaluating 20 specific security failure modes, contrasting current controls against identified gaps, and specifying the mandatory mitigations required prior to live activation.

---

| **15** | **Provider Impersonation**<br>Attacker spoofing Safaricom or Sendy servers using self-signed certificates or DNS spoofing. | Outbound HTTPS requests use standard Node.js CA certificates. | Development environments might disable SSL verification (`rejectUnauthorized: false`). | Strict production TLS certificate validation (`rejectUnauthorized: true`) on all outbound provider HTTP clients. | **Phase 6.5**<br>(Infrastructure) |
| **16** | **External API Timeouts**<br>Safaricom Daraja takes $> 30\text{s}$ to respond, hanging Fastify server connections. | Node.js asynchronous I/O; non-blocking database queries. | Synchronous awaiting of slow external APIs can exhaust server threadpools. | Enforce strict 8000ms timeout on outbound Daraja calls; return HTTP 202 Accepted and delegate resolution to webhooks. | **Phase 6.6**<br>(Live Payments) |

## 3. Required Security Roadmap Summary

Prior to live activation:
1. **Network & Webhook Perimeter**: Implement IP filtering and HMAC verification on `/api/webhooks/mpesa`.
2. **Cryptographic Identity Protection**: Transition session cookies to `secure: true` under managed HTTPS.
3. **Storage Isolation**: Enforce private S3 buckets with ephemeral presigned URLs for all medical and optical attachments.
4. **Idempotent Financial Settlement**: Enforce unique receipt constraints and database row locks to eliminate double-billing and replay vulnerabilities.
